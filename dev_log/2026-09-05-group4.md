# 2026-09-05 Acceptance Group 4 — 持仓安全与恢复

## Requirement

在系统已有仓位后，无论正常运行、AI 延迟、Pause、Emergency Stop、数据异常、进程重启或数据库恢复，都不因 Runtime 状态混乱产生未经授权的新风险，并尽最大可能继续保护已有仓位。安全性优先于功能数量。

## Scope

- Position Protection（Stop Loss / Take Profit / Protective Exit / Exit Reason / Idempotency）
- Position Re-evaluation（HOLD/ADD/REDUCE/CLOSE/CANCEL_ADD/UPDATE_STOP/UPDATE_TP/UPDATE_INVALIDATION/REPLACE_PLAN）
- System Safety State（STARTING/RECOVERING/RUNNING/PAUSED/DATA_DEGRADED/SAFE_MODE/EMERGENCY_STOP/ERROR）
- Control（Pause/Resume/Emergency Stop/Emergency Recovery/Symbol Block/Manual Close/Cancel Order/Safe Mode）
- Recovery（PostgreSQL SoT / Restart Recovery / Reconciliation Gate / Plan & Order Revalidation / EXECUTION_GAP）
- 最小 Health Registry 与 Incident Manager

## Out of Scope

Live Trading、Contract/Short、Leverage、Liquidation、Grid、Full Backtest、Replay Engine、Dashboard、React UI、Performance Analytics、Batch AI Review、WeCom、Model Committee、AI 自动改策略、Redis/Kafka/RabbitMQ/Celery、Microservices、K8s、Close All、Complex Trailing Stop、自动反手、多用户/RBAC。

## Implementation

### Persistence / Migration
- `20260905_0004_group4_position_safety`：`trades.exit_reason`（nullable 附加列）+ `runtime_controls` / `symbol_controls` / `incidents` / `position_events`（含 `uq_position_events_dedupe`）。基于 `20260904_0003`，upgrade head / current / heads 一致。

### System State
- `SystemStateService`：持久化 `operator_state`（NORMAL/PAUSED/EMERGENCY_STOP）与 `system_state`、`runtime_version`、`reason`、`updated_at`、`heartbeat_at`、`payload`。
- `effective_state()`：Operator Intent 优先级最高（EMERGENCY_STOP → SAFE_MODE 锁存 → PAUSED → STARTING/RECOVERING → ERROR → DATA_DEGRADED → RUNNING）。重启不会把 EMERGENCY_STOP 错恢复为 RUNNING。

### Risk Gate
- `SystemRiskGate`：唯一程序化风险准入。先 `FOR UPDATE` 锁 runtime_control 行，再查 effective state / health（DATABASE·CORE_MARKET_DATA·EXECUTION）/ blocking incident / Symbol Block / Plan validity。仅拦截 BUY；SELL 风险降低永不拦截。

### Protection
- `PositionProtectionService`：SL（bid ≤ stop）/ TP（bid ≥ tp）触发保护退出；数据 stale Fail Closed + `CORE_DATA_STALE` incident，恢复后立即重评。成交价恒为 live bid − slippage，绝不用 stop/tp/snapshot 价。退出前先取消该 Symbol 所有 OPEN BUY（防 stale add 重新持仓）。幂等由确定性 `intent_id` + `paper_orders/fills.intent_id` 唯一约束 + `position_events.dedupe_key` 唯一约束 + Position 行锁保证。

### Position Re-evaluation
- `PositionReevaluationService`：MeaningfulEventGate（min interval / price move / state version 变化）防每 tick 调 AI；不可变 DecisionSnapshot + AIDecisionRecord 沿用 G3 审计链。9 种动作程序化验证后派发：ADD 需 RUNNING+capacity（替换 plan + 同一事务执行，拒绝即回滚，保护不丢）；REDUCE/CLOSE 在 RUNNING/PAUSED/SAFE_MODE/EMERGENCY 下仍可执行；CANCEL_ADD 幂等释放 Reservation；UPDATE_*/REPLACE_PLAN 生成新 plan version，旧 plan REPLACED，stale 风险单取消。
- AI 失败（timeout/schema/business/stale/unavailable）→ 保留 SL/TP、记 `AI_REEVALUATION_FAILED`，绝不增仓/平仓/改保护。

### Control
- `SystemControlService`：pause/resume（resume 为 gate：DB+reconciliation+health+fresh data+无 blocking incident+非 emergency 全过才 RUNNING）；emergency_stop（单事务取消所有 OPEN BUY 并释放 Reservation，≠ Close All，保护继续）；emergency_recovery（EMERGENCY→校验→PAUSED，绝不直连 RUNNING）；block/unblock symbol（bump G2 state_version + 取消该 Symbol OPEN BUY）；enter/recover safe mode（SAFE_MODE 锁存，显式恢复→PAUSED→人工 resume）；manual_close（Full Close，ExitReason=MANUAL_CLOSE）。

### Reconciliation（G4 扩展）
- 复用 G3 六项不变量，追加 7–12：active plan 唯一、OPEN order 关联有效 plan、EMERGENCY 下无 OPEN BUY、closed position 无 stale sell intent、account/position 非负、runtime control 内部一致。纯 Detector，不自动修库。

### Recovery
- `RecoveryManager`：STARTING→RECOVERING→Load runtime control/account/orders/positions/plans/symbol states→active symbols→Fresh BBO→EXECUTION_GAP 审计→reconciliation→plan/order revalidation（stale BUY 取消释放 Reservation）→restore protection 并立即评 SL/TP→决定 final state→heartbeat。全部从 PostgreSQL 重建，不依赖内存；停机穿价以恢复后当前 BBO 成交，不伪造历史 Fill。

### Health / Incident
- `HealthRegistry` 增 `status/blocking/all_healthy`；`IncidentManager` 最小持久化（7 类 incident，idempotent open，resolve）。

## Concurrency

- 同 Symbol：进程内 asyncio lock + PostgreSQL 行锁（runtime_control 先行，避免死锁）。
- Emergency vs BUY Fill、Manual Close vs SL、重复 SL/TP：由 runtime_control 锁 + order/position 行锁 + 唯一约束保证一致性。

## Failure Injection（真实回滚）

- Protective settlement / emergency cancel / plan replace / manual close 注入失败后，Order/Fill/Position/Account/Ledger/Reservation/Plan 保持事务前一致，无 half-commit。

## Post-Review Fix #3（G4 Acceptance Review #3 = FIX REQUIRED）

### Requirement / Scope

- 修复 `POSITION_UNPROTECTED` 的 SAFE_MODE recovery 证明缺口，并防止错误标记 `RESOLVED` Incident 后普通 Resume 让未真实保护的 OPEN LONG 进入 `RUNNING`。
- Scope：仅 G4 plan loading/business validation、control gates 与真实 PostgreSQL regression tests。
- Out of Scope：PostgreSQL transaction / lock ordering 重设计、Protection Engine、自然语言 invalidation parser、G5、main merge、Live Trading。

### Implementation

- `load_active_plan()` 只接受 exactly one ACTIVE durable row；必须能经 `TradePlan.model_validate` 解析，且 payload 与 row 的 plan identity、run_mode、instrument、state/plan version、status、timestamps 一致。任何 raw/corrupt/mismatched durable evidence 都 fail closed。
- 共用 `plan_business_errors()`；它保留既有 entry-zone 与 SL/TP 可执行关系检查，并在 OPEN LONG proof 中验证 `stop_loss < position.average_cost < take_profit`。
- `SystemControlService._open_position_protection_gate()` 复用 `load_valid_long_active_plan()`。`safe_mode_recovery()` 与 `resume()` 都通过该 gate；因此错误手工 RESOLVED Incident 不是放行依据。
- 未改动 `TradePlan.invalidation` 的语义或解析行为。

### PostgreSQL Regression

1. ACTIVE row 的 corrupt payload 与可解析但 plan identity mismatch payload 都使 Safe Mode Recovery 拒绝，保持 `SAFE_MODE`，`POSITION_UNPROTECTED` 保持 OPEN。
2. payload 可解析但 LONG protection relationship 非法（stop 高于当前 average cost）时 Recovery 拒绝并保持 `SAFE_MODE`。
3. 修复为有效 Active Plan 后，Safe Mode Recovery 才 resolve blocking incident 并落到 `PAUSED`。
4. 随后 manual Resume 在错误 RESOLVED Incident + 非法保护时仍拒绝；仅在有效保护、healthy/fresh core data 与 reconciliation 全部满足后进入 `RUNNING`。
