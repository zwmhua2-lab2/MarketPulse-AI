## Task

G5-4 — Deterministic Replay Evaluation。在 G5-3 ACCEPTED 的 deterministic Replay 之上，从完成后的
Replay PostgreSQL durable workspace 生成 `ReplayEvaluationReport`，使系统能够回答：

> 这次可信、可重复的 Replay 最终产生了什么确定性的交易与经济结果？

只做最小、可信、可重复的 Evaluation Layer。不是 Full Backtest Platform、不是 Performance Analytics
平台、不是 UI、不是 AI Review。

## Requirement

| 编号 | 需求 |
|---|---|
| R1 | 指标事实源只能是 Replay PostgreSQL durable business facts |
| R2 | 确定性读取：`REPEATABLE READ, READ ONLY` + primary key 稳定排序 + `math.fsum()` 聚合 |
| R3 | 不自欺：durable facts 不足以无歧义证明的指标不做 |
| R4 | fail closed：fill 无 order、side 未知、account 不唯一、quantity < 0、未知 trade status、fee mismatch |
| R5 | A/B 评估与摘要完全相等；A/C 摘要不等且存在真实经济字段变化 |
| R6 | 三个会计指标（`account_realized_pnl` / `total_fees` / `ledger_cash_delta`）分别报告，不合并 |
| R7 | 不持久化、不新增 schema、不引入 `replay_run_id` / `backtest_id` |

## Implementation

### `backend/src/marketpulse/g5/evaluation.py`（新增）

- `ReplayEvaluationError(RuntimeError)`：所有 fail-closed 路径统一抛出。
- `ReplayEvaluationReport`（frozen dataclass）：23 个字段（21 个评估指标 + `workspace_digest` + `evaluation_digest`），见「Metric Semantics」。
- `evaluate_replay_workspace(engine, *, workspace_digest)`：
  - 在单个 `REPEATABLE READ, READ ONLY` 事务内按 primary key 排序读取 durable facts；
  - fill 分类经 `FillRecord.order_id → PaperOrderRecord.order_id → side` 取得真实方向；
  - 全部 float 聚合用 `math.fsum()`；整数计数用 `func.count()`（精确，非 float 聚合）；
  - 成功返回前执行 accounting consistency 校验；
  - `evaluation_digest` 由 `canonicalize_value()` + deterministic JSON + UTF-8 + SHA-256 得出。
- `_verify_accounting(...)`：把报告值与 durable 值逐项对账（含对 account 的独立二次读取）。

### `backend/src/marketpulse/g5/replay.py`（最小 additive）

- 新增 import：`ReplayEvaluationReport`、`evaluate_replay_workspace`。
- `ReplayTradingResult` 末尾新增 `evaluation: ReplayEvaluationReport | None = None`
  （`_run_in_workspace` 不传，保持默认 `None`）。
- `run()` 流程：`capture canonical workspace → workspace_digest → evaluate durable workspace →
  verify primary unchanged → return`。Evaluation 从 Replay DB 重新读取，不使用
  `result.fills / result.trades / result.final_account`。

### Evaluation Digest Contract

- 规范化复用 G5-3 `canonicalize_value()`（float → hex、Decimal → exact、datetime → UTC、
  dict key 排序、array 保序、type-tagged 无歧义）。
- 序列化：deterministic JSON（`ensure_ascii=False` / `sort_keys=True` / `separators=(",", ":")` /
  `allow_nan=False`）→ UTF-8 → SHA-256 hex。
- 排除 `workspace_digest`：它是 provenance，evaluation digest 必须只因「评估经济结果变化」而变。

## Accounting Semantics

当前 accepted G3 settlement semantics（**未修改**）：

- SELL：`realized = (price - average_cost) * quantity - SELL fee`；`cash_delta = gross - fee`。
- BUY：`realized = 0`；`cash_delta = -(gross + fee)`；BUY fee 从 `cash_balance` 扣除，**不进**
  `account.realized_pnl`。

因此三个字段**不可混同**：

| 字段 | 含义 |
|---|---|
| `account_realized_pnl` | 仅 SELL 结算累计 realized（已扣 SELL fee，不含 BUY fee） |
| `total_fees` | 全部 Fill fee（BUY + SELL） |
| `ledger_cash_delta` | 全部 ledger cash 变动（BUY 付钱 + SELL 收钱，均含 fee） |

真实证据（Run A）：`account_realized_pnl = -111.77866566716638`、
`total_fees = 1.889110444777611`、`ledger_cash_delta = -112.77866566716636` — 三者互不相等，
未创建任何 `profit` / `net_profit` 合并字段。

### 需要如实说明的一处偏差（Self Review Fix #1 已收紧）

`final_cash_balance - configured_initial_cash == ledger_cash_delta` 在**位精确**意义下不成立：
两侧对同一组 cash movement 的累加顺序不同（账户余额为顺序累加，ledger 侧为 `fsum`），产生的是
**二进制浮点 IEEE-754 对账边界（ULP 量级）**，而非会计差异。Self Review Fix #1 以真实测试值重新
测量：flat fixture 实测差 = `5.684341886080801e-13`（约 `5.68e-13`）；旧文档误记为 `2e-14`，
已据实测值更正。

测试现以**机器精度派生**的容差替代固定 `1e-9`：

```text
cash_change = report.final_cash_balance - INITIAL_CASH
abs_tol = 4 * max(
    math.ulp(report.final_cash_balance),
    math.ulp(INITIAL_CASH),
    math.ulp(report.ledger_cash_delta),
)
assert math.isclose(cash_change, report.ledger_cash_delta, rel_tol=0.0, abs_tol=abs_tol)
```

实测 `abs_tol ≈ 7.28e-12`（= 4×ULP），仍比任何真实会计差异（≥ 0.01）小约 9 个数量级；这是
**二进制浮点对账边界，不是会计不匹配容差**。该容差可据真实证据进一步收紧，但禁止退回固定的大
tolerance（如 `1e-9`）。
